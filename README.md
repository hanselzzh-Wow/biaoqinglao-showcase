# 表情捞

**截图进来，表情出去。**

<br clear="left">

在群里看到一张想用的表情，现在的做法是截图、裁剪、存相册，再从另一个 App 发出去，而且每转一手画质就差一截。表情捞把这几步压成一步：截一张表情面板，App 认出里面的每一张表情，自动切好，再换成高清原图。

## 三个设计决定

### 1. 截图不离开手机

图像特征用 Apple Vision 在手机上提取，上传到服务端的只有一串特征值和 OCR 出来的文字，截图本身不上传。App 首页也直接写明了这一点：「截图不会离开这台手机」。

### 2. 端云两级检索，只用一把尺子做决定

手机上有一份压缩索引（PCA-192、int8），服务端是 768 维全精度、多尺度的完整索引。早期版本拿本地的置信间距和服务端的直接比大小。**这两个数虽然都叫 margin，但分母来自两个不同的候选分布，本来就没法比较。** 后来改成客户端把本地候选一起发给服务端，服务端把它们并进自己的候选池，在同一套几何里重新排序。服务端给出的答案就是最终答案，其中也包括它说「不敢换」的情况。

### 3. 版权靠事后治理，底线一票否决

表情包天然来自用户创作。如果要求每一张都先拿到书面授权，这个产品就不可能启动。所以采用避风港式的事后机制：权利人申诉 **4 小时内初审，24 小时内下架**，处理链路和台账都已经建好。唯一不讨论的底线是涉及未成年人的真人素材和法律明令禁止的内容：发现即撤，不走申诉流程。

## 匹配质量：数字和它们的局限

下面的数字都来自合成退化的截图测试集，只能用来比较改动前后有没有进步，**不能代替真实用户截图的验收**。

| 指标 | fresh（494 条） | hard（500 条） |
| --- | --- | --- |
| Top-1 / Top-3 | 90.1% / 97.2% | 74.4% / 86.0% |
| 自动替换覆盖率 / 错误数 | 71.5% / 0 | 37.6% / 1 |
| 库外图片被误换率 | 1.4% | — |
| 服务端单次查询中位耗时 | 10.4 ms | 10.7 ms |

服务端单次查询耗时从 136.6 ms 降到约 10 ms，主要是把每次查询都要重算的授权状态改成了缓存。

### 一个没上线的重排模型

Top-3 有 97%，Top-1 却只有 90%，看起来中间有 7 个点的提升空间。于是训练了一个候选级的重排模型，结果 Top-1 只从 90.1% 升到 90.3%，494 条里只多对 1 条。

把这中间的 36 条查询逐条摊开看：它们和视觉第一名的分差，中位数只有 0.016，83% 落在 0.03 以内；能单靠 OCR 文字区分出来的只占 22%。重排确实救回了 12 条，但也弄错了差不多同样多条。

**结论：这些错误落在视觉表示本身分不开的区间里，换一个排序器只是让错误换个位置。** 真正要改的是表示本身（做表情专用的度量模型），或者补真实标注（建真实截图测试集），而不是排序器。所以这个重排模型没有接进服务端，没有给发布链路增加一个没有收益的产物。结论和复现方法都留在了实验记录里。

## 现在的边界

- 匹配服务目前跑在个人 Mac 上，由 LaunchAgent 托管。机器休眠或断网时公网接口就不可用。要长期运营，需要迁到常驻服务器
- 质量数据以合成测试集为主，真实截图测试集还在建
